# ③ インタラクティブ推論（What-if スライダー）設計書

**対象**: Web版のみ（`IS_TAURI === false`）
**位置づけ**: Web版の③ CSV一括予測を廃止し、スライダー操作によるリアルタイム単一行予測に置換する。
CSV一括予測はexe版の役割とし、Web版③には「大量データの一括予測はデスクトップ版で」の導線だけ残す。
**日付**: 2026-07-31 起案 / 2026-08-01 実装完了（Phase 1–6）

---

## 0. 結論サマリ

「スライダーを動かすと数値が変わる」だけの素朴な実装は、辛口レビューで挙がった6つの穴
（特徴量過多での破綻／外挿の隠蔽／ceteris paribus の非現実性／開発コスト／トーン不一致）を
そのまま踏む。本設計はそれぞれに具体的な対策を割り当てた上で、**予測ロジックには一切触らない**
（既存の検証済みJSエンジンを呼ぶだけ）ことで実装リスクを最小化する。

技術調査で判明した重要な事実：

| 事実 | 出典 | 意味 |
|---|---|---|
| `.treg` は**デプロイ時ではなく学習完了時**に書き出される | `train_bridge.py` L3329-3377（`_emit_progress(96, "saving_model")` 直後） | ④を押す前から推論可能 |
| Web版は学習完了時に `_lastTreg` に treg バイト列を**既にメモリ保持**している | `frontend/index.html` L1776 | モデル取得の追加配線が不要 |
| 単一行予測プリミティブ `predictRow(model, row, rawRow)` が既に存在する | `web/js_predict_poc/predict-core.js` L561, L587 | 推論ロジックの新規実装ゼロ |
| `rawRow` は「CSVの生文字列 colname→string」を受ける | 同 L293-301 | スライダー値をそのまま渡せる |
| 派生特徴量・カテゴリエンコード・y変換・後処理は**エンジン内部で完結** | 同 `buildFeatureVector` L518 / `predictRow` L580-584 | UI側は生列だけ管理すればよい |

→ **`.treg` バイナリ形式は変更しない**ため、CLAUDE.md ルール3（4点セット同時変更）および
ルール7（3実装パリティ）は**発動しない**。守るべきはルール1（frontend/index.html 単一ソース）と
ルール2（ルート/`web/py/` の Python 複製同期）のみ。

## 3. データ契約（`train_bridge.py` → result JSON への追加フィールド）

既存の学習パイプラインには手を入れず、`result` 辞書（L3263-3319）に以下を追加する。
`_sanitize_json` を通るため NaN/Inf 対策は既存機構に乗る。

### 3.1 `slider_spec`（必須）

スライダー1本 = 生CSV列1つ。**engineered feature ではなく raw column** で出すことが要点。

```jsonc
"slider_spec": [
  {
    "col": "temperature",          // 生CSVの列名
    "kind": "numeric",             // "numeric" | "categorical" | "datetime"
    "importance_pct": 34.2,        // §3.2 で raw 列へ集約した重要度
    "median": 22.5,                // 初期値・固定値として使う
    "p1": 8.0, "p99": 41.0,        // 外挿判定境界（この外はamber）
    "min": 5.2, "max": 44.8,       // スライダー端（データ実測レンジ）
    "step": 0.1,                   // (p99-p1)/200 を有効数字1桁に丸めた値
    "hist": [3,9,21,40,55,48,30,12,5,2],   // トラック背景の密度（20 bin）
    "hist_lo": 5.2, "hist_hi": 44.8,
    "x_clip_lo": 6.0, "x_clip_hi": 43.0,   // .treg の x_clip 相当（§5.4）。無ければ null
    "is_integer": false
  },
  {
    "col": "city",
    "kind": "categorical",
    "importance_pct": 12.8,
    "mode": "Tokyo",                        // 初期値
    "levels": [                             // 出現頻度降順、最大30件
      {"value": "Tokyo", "count": 412},
      {"value": "Osaka", "count": 188}
    ],
    "truncated": false                      // 30件超で切った場合 true
  }
]
```

生成箇所: `train_bridge.py` の result 組み立て直前。`df`（`_prepare_categoricals` **前**の
生データフレーム）と `target_column` から算出する。カーディナリティ超過で除外された列
（`cat_dropped_cols`）と、モデルが実際に使っていない列は**含めない**。

### 3.2 raw列への重要度集約

`feature_importance` は engineered 名（one-hot `city=Tokyo`、target-encoded、派生 `a*b`、
poly `x0 x1`）かつ上位10件に切られており、そのままスライダー順序に使えない。集約規則：

| engineered 名の由来 | 集約先 |
|---|---|
| 生列そのまま | その列に全額 |
| one-hot `col=value` | `col` に合算 |
| target encoding / composite target encoding | `source_col`（複合キーは構成列に等分） |
| datetime_parts | 元の datetime 列に合算 |
| 派生 `a*b` / `a**2` / `sign(a)` | 構成列に等分（`a**2`, `sign(a)` は `a` に全額） |
| poly `x_i x_j` | `x_i`, `x_j` に等分 |

集約は**上位10件に切る前の全特徴量**に対して行う（切ってから集約すると寄与が欠ける）。
そのため `feat_list` 生成箇所（各 `_try_*` 関数）で切る前の全量を `info` に保持し、
result 組み立て側で集約する。集約後に降順ソートして `slider_spec` に載せる。

### 3.3 `y_hist`（必須・ヒストグラム本体）

**既存の `scatter.true` は使わない**。最大250点にサブサンプルされ、かつ評価行のみ
（`train_bridge.py` L3194-3197）で全体分布ではない。全学習行 `y_raw_all` から算出する。

```jsonc
"y_hist": {
  "bin_edges": [0.0, 5.0, 10.0, ...],   // Freedman–Diaconis、最大40bin
  "counts": [3, 12, 48, ...],
  "n": 1284,                             // 学習行数
  "p10": 8.2, "p50": 24.1, "p90": 61.0   // 分位マーカー用
}
```

### 3.4 `seed_rows`（必須・§6.1 の実データ初期値）

```jsonc
"seed_rows": [
  {"label": "median", "y": 24.1, "values": {"temperature": "22.4", "city": "Tokyo"}},
  {"label": "high",   "y": 78.9, "values": {...}},   // y の p90 近傍
  {"label": "low",    "y":  6.2, "values": {...}},   // y の p10 近傍
  {"label": "random", "y": 31.0, "values": {...}}    // 固定seedで3件
]
```

`values` は **生CSV文字列**（`predictRow` の `rawRow` にそのまま渡せる形）。

### 3.5 `neighbor_ref`（推奨・§6.2 の妥当性ゲージ）

```jsonc
"neighbor_ref": {
  "cols": ["temperature", "pressure"],   // 数値列のみ
  "mean": [22.5, 101.3], "std": [6.1, 2.4],
  "weight": [2.31, 0.88],                // 重要度由来の次元重み（平均1に正規化）
  "rows": [[0.12, -0.88], ...],          // 標準化済み、最大300行にサブサンプル
  "radius": 3.49                          // §6.2 の判定半径（Python側で算出）
}
```

300×数値列数の float。50列でも 15000 個 ≒ 数十KB で、result JSON を圧迫しない。

**`weight` が必須である理由（モック実測で判明）**: 重みなしの素朴なユークリッド距離では、
数値列48本のデータで**実在する学習行すら近傍0件**になった（次元の呪い。無関係な列のノイズが
距離を支配する）。`weight[j] = importance_pct[j] / Σimportance × ncols` で重み付けし、
`d = sqrt(Σ w_j (z_j - q_j)^2)` とすることで解決する。重要度0の列にも下限 0.01 を与え、
完全に無視はしない。

### 3.6 `corr_pairs`（推奨・§6.3 の連動警告）

```jsonc
"corr_pairs": [
  {"a": "temperature", "b": "pressure", "r": 0.87, "slope": 0.34, "intercept": 93.6}
]
```

`|r| >= 0.7` の数値列ペアのみ。`slope`/`intercept` は b を a に追従させる連動モード用の
単回帰係数。ペア数は |r| 降順で最大20件。

### 4.2 対策②: 特徴量過多への対応（スクロールと目線移動の最小化）

**方針**: 変数が多くても「スクロールしない・目線を動かさない」を優先する。
そのために (a) 1変数の縦寸法を圧縮し、(b) 横方向に折り返し、(c) 応答側を固定する。

**(a) スライダー1本 = 1行 26px**

名前・トラック・値・感度スパークラインを2段組みではなく**横一列**に収める。

```
[重要度][列名 84px][── 密度トラック（可変）──][値 52px][感度 40px][×]
```

- 重要度は数値ではなく、左端の縦バーの高さ（3px 幅）で表す
- カテゴリ列はピルを**折り返さず横スクロール**させ、行の高さを一定に保つ
- v2 の2段組み（46px/本）から **44% 圧縮**

**(b) 左ペインを可変列グリッドに**

`grid-template-columns: repeat(auto-fill, minmax(258px, 1fr))` で、ペイン幅に応じて
1列→2列→3列に自動で折り返す。実測の縦寸法:

| 変数の数 | 1列 | 2列 | 3列 |
|---:|---:|---:|---:|
| 6 | 156px | 78px | 52px |
| 12 | 312px | 156px | 104px |
| 18 | 468px | 234px | 156px |
| 30 | 780px | 390px | 260px |
| 50 | 1300px | **650px** | **442px** |

右ペイン（予測数値＋密度カーブ＋ステータス）の高さは約250px。
**3列表示なら30変数まで右ペインと同じ高さに収まり、スクロールがまったく発生しない。**
50変数を全表示しても442px で、1画面に収まる。

**(c) 右の予測パネルは `position: sticky`**

左をスクロールしても予測値・分布・近傍リングは常に同じ位置に留まる。
「左で操作 → 右で結果を見る」の目線移動が固定され、スクロール位置に依存しなくなる。
狭幅時（< 820px）は縦積みに切り替え、予測パネルを**上**に置く（sticky は解除）。

**表示本数のポリシー**

- 既定は重要度上位 **12本**（2列で156px。ほとんどの画面でスクロールなし）
- ツールバーの `▾ 38` を1クリックで**全列をスライダー表示**（上限撤廃）。もう一度押すと戻る
- 残りは「FIXED n」ラベル付きのチップを**1行に収めて横スクロール**（縦を増やさない）
- チップクリックで昇格。挿入位置は**重要度降順を維持**（押した順に並ばない）
- チップが12個を超えたら絞り込み入力を出す
- 変数が既定本数以下なら、展開ボタンも FIXED 行も**丸ごと消える**
- 昇格／降格の状態は `localStorage` に保存しない（学習ごとに列構成が変わるため）

### 4.3 スライダーの型別表現

| kind | UI |
|---|---|
| numeric | `<input type="range">` + 数値直接入力ボックス（範囲外入力は clamp して警告） |
| categorical | セグメントピル（6件以下）／`<select>`（7件以上） |
| datetime | 日付入力 `<input type="date">`（`datetime_parts` エンコーダがある列のみ） |

`is_integer: true` の列は `step: 1` を強制し、小数を出さない。

## 5. 対策③: 過信を防ぐ表示設計（最重要）

### 5.1 点ではなく帯で見せる

予測値は必ず `38.4 ± 5.2` の形で出す。`±` の幅は **検証RMSE**（既存 `result.rmse`）。
ヒストグラム上のマーカーも縦線1本ではなく **±1×RMSE の半透明帯 + 中心線**として描く。

これにより「R²が低いモデルほど帯が自動的に太くなる」= 精度の低さが視覚的に自己申告される。
`rmse` が `null` の場合は帯を描かず、代わりに「精度指標なし」と明記する。

### 5.2 低精度時の減光

- `r2 < 0.5` または `r2_reference_only === true` のとき:
  ヒストグラム全体の不透明度を 0.55 に落とし、中央に薄い「REFERENCE ONLY」透かしを重ね、
  予測値の色を `--ink-dim` にする（`--cyan` の強調をやめる）。
- パネル冒頭に既存の `r2_interpretation` 文言をそのまま1行表示する（新規文言を作らない）。

### 5.3 スライダートラックへの密度描画（外挿の可視化）

各 numeric スライダーのトラック背景に `hist`（20bin）を淡いバーとして描く。疎な領域が
一目で分かるため、「動かせるが根拠が薄い場所」がUI上に自然に現れる。

つまみが `p1`〜`p99` の外に出たら:
- そのスライダーの数値ラベルとつまみを `--gold` に変える
- 予測パネルに `⚠ 外挿中: <列名>` を列挙（3件以上は「他N件」）

### 5.4 x_clip 境界の説明責任

`.treg` は特徴量ごとに `x_clip_lo/hi` で入力をクリップする（`predict-core.js` L532-534）。
このため境界外へスライダーを動かしても**予測が一切動かない**。無言だと「壊れている」と
誤解されるため、境界に達したらつまみに停止マークを出し、
「学習範囲の外は予測が飽和します（モデルの安全機構）」と明示する。

`x_clip` は engineered feature index に対する値なので、**生列と1:1で対応する特徴量に限り**
`slider_spec.x_clip_lo/hi` に載せる。派生・エンコード列経由の場合は `null` とし、
この表示を出さない（誤った境界を見せるより出さない方が安全）。

### 5.5 パーセンタイル表記

`y_hist` から「予測値は学習データ分布の上位 18%」を計算して添える。ただし §5.2 の低精度時は
この表記も出さない（精度が低い予測に順位を付けると過信を招く）。

## 6. 対策④: ceteris paribus 問題への対応

### 6.1 初期値は「中央値の合成行」ではなく実データ1行

全列を中央値で埋めた行は、相関のあるデータでは**実在しない組み合わせ**になりうる。
`seed_rows` から選んだ実行を出発点にする。既定は `median`（y中位の実行）。
セレクタで `high` / `low` / `random` に切替可能。「リセット」は選択中のseed行に戻す。

副産物として、seed行は正解 `y` を持つので **「実測 24.1 → 現在の予測 38.4」** という
対比が出せる。これは単独の予測値より遥かに情報量が多い。

### 6.2 近傍件数ゲージ

`neighbor_ref` を使い、現在のスライダー組み合わせを標準化・重要度重み付けしてから
学習行サンプルとの距離を計算し、**半径内に何件あるか**を出す。

**判定半径の定義（モックで検証済み）**:
「各学習行から**10番目に近い行**までの重み付き距離」を全行について求め、その**中位数**を半径とする。

この定義には次の性質がある。
- 実在する学習行を入れると近傍は概ね10件前後になる（構成上そうなる）
- 非現実的な組み合わせでは0件になる
- **次元数に依存しない**ため、列数が3本でも50本でも同じ意味で読める

素朴な「全ペア距離の中位数×0.5」を使った当初案は、48列のモックで**実在する行すら0件**に
なり使えなかった（§3.5 参照）。半径は Python 側で算出して `neighbor_ref.radius` として渡す
（JS側で全ペア距離を計算するとサンプル120行でも1万回超のループになるため）。

表示:
- 「近い実データ: 12件」（3件未満は amber、0件は red）
- 0件のときは `⚠ 学習データに似た組み合わせがありません` を強調表示
- 数値列がゼロのデータでは「算出不可（数値列なし）」と明示
- 1回の判定は300行×数値列数の総当たりのみ（1ms未満）

「距離0.83」のような抽象値ではなく**件数**で出すのが要点。非専門家にも意味が通る。

**モックでの実測挙動**（`docs/interactive-predict-mock.html`、800行×50列）:

| 入力 | 近傍件数 | 解釈 |
|---|---|---|
| 実データ4行（median/high/low/random） | 9 / 10 / 14 / 9 件 | 妥当と判定 ✓ |
| 全列を最大値にした行 | 0 件 | 非現実的と検出 ✓ |
| temperature だけ最大・pressure は中央値固定 | **0 件** | **ceteris paribus 違反を検出 ✓** |

3行目が本設計の要点。相関する列を固定したまま1変数だけ極端に動かすと、
ユーザーが気付く前にゲージが0件になって警告する。

### 6.3 強相関ペアの明示と連動モード

`corr_pairs` を使い、動かしたスライダーに強相関の相手がいる場合:

- そのスライダー下に小さく `pressure と連動 (r=0.87)` と表示
- トグル「連動モード」ON時、`slope`/`intercept` で相手を自動追従させる（追従されたスライダーは
  つまみを破線にして「自動」であることを示す）
- 連動モードは既定 **OFF**。ただし OFF のまま強相関の片方だけを大きく動かしたときは
  「相関する列が固定されています」と注意を出す

線形の追従は近似にすぎないが、「1変数だけ動かすのが自然だ」という誤解を解く役割としては十分。

### 6.4 感度スパークライン（1変数の影響を"形"で見せる）

各スライダー右端に、その列だけを min→max に振ったときの予測値カーブを 24px 高のスパーク
ラインで描く。単調増加なのか、山型なのか、ほぼ平坦なのかが一目で分かる。

- 計算コスト: 列数 × 25点 の `predictRow` 呼び出し（10列なら250回）
- **ドラッグ中は再計算しない**。`pointerup` / `change` 後の `requestIdleCallback` で更新
- LightGBM の木が多い場合でも 250回 × 数百µs = 数十ms 程度。UIブロックを避けるため
  8列ずつ分割して連続する rAF に散らす

これが「見た目のかっこよさ」と「実利」が最も一致する要素。ヒストグラムより先に実装する価値がある。

## 7. 情報量の削減方針（「説明せずに分かる」）

機能は一切減らさず、**画面に出す文字を減らす**。原則は「文章で説明していたものを、色・形・
位置で表現し、文章は `title` 属性に退避する」。モック実測で画面上の文字数は 261→254字、
`title` を持つ要素は50個（＝説明は失われていない）。

| 従来（文章） | 置換後（見れば分かる形） |
|---|---|
| 「学習データの外側 (p1–p99: 7.78–36.73)」 | 密度カーブの裾がゼロに落ちる形＋つまみが amber になる |
| 「■ 学習範囲の外は予測が飽和します（モデルの安全機構）」 | トラック端に**壁**を描き、つまみが丸→**角**に変わって壁に張り付く |
| 「pressure と強く相関 (r=0.88) — 固定されています」 | 相関相手が示す**ゴーストつまみ**（中空の丸）を同じトラック上に置き、ズレを破線でつなぐ |
| 「近い実データ: 12件」＋ラベル | **リングゲージ**（満ちる＝安全／欠ける＝危険／赤＝0件）＋中央に数字ひとつ |
| 「あてはまりが弱く、個々の予測値の…」（R²解説文） | 右パネル全体の**彩度を落とす**＋誤差帯の幅そのもの |
| 「基準行の実測 88.52 → 現在の予測 87.30」 | 分布上に**緑の中空リング**（実測）と予測マーカーを並べて置く |
| 「予測値は学習データ分布の 上位 54%」 | マーカーの位置がそのまま順位を示す（数値は `title` へ） |
| 重要度「34.2%」 | 列名の隣の**細いバー**の長さ |
| カテゴリの件数「(412)」 | ピルの `title` へ |
| 「固定に戻す」ボタン | ホバー時に現れる `×` |

### 7.1 ヒストグラム → 密度カーブ

棒グラフ（ビン）をやめ、Catmull-Rom 相当の**滑らかな密度カーブ**にする。同時に以下を撤去:

- 外枠（`strokeRect`）
- y 軸の目盛りと件数ラベル
- 軸タイトル「件数」「yield の分布（学習データ800行）」

残すのは、ベースラインの薄い水平線と x 軸の数値3つ（最小・中央・最大）のみ。
`drawScatter` の pad 規約は撤廃し、余白は `{l:8,r:8,t:14,b:18}` まで詰める
（散布図と違い、密度カーブは軸目盛りを必要としないため）。

スライダーのトラック背景も同じ扱いで、20本の棒 → 28点の密度カーブに変更する。

### 7.2 削減してはいけないもの

以下は情報量削減の対象外とする（削ると安全機構が消えるため）。

- 誤差帯 `±RMSE`（帯の描画と数値の両方）
- 外挿・飽和のフラグ（文字は列名のみに短縮するが、表示自体は残す）
- 近傍リング
- 感度スパークライン

## 8. 対策⑥: トーンの統一

- **新規CSS変数を作らない**。既存の `--cyan` `--gold` `--good` `--ink-dim` `--ink-faint`
  `--hairline` `--surface` `--font-display` `--font-mono` のみを使う。
- Canvas描画は `drawScatter`（`frontend/index.html` L2201-2290）の作法をそのまま踏襲:
  `devicePixelRatio` スケール、`pad = {l:46, r:12, t:10, b:34}`、罫線 `rgba(160,190,220,0.08)`、
  軸 `rgba(160,190,220,0.25)`、目盛りフォント `10px system-ui`、ラベル `rgba(180,200,225,0.75)`。
- グローは既存 `.feature-line` と同等（`0 0 8px <color>60`）に抑える。派手な多重グローは使わない。
- アニメーションは**予測マーカーの移動のみ**（120ms ease-out）。スライダー操作に対する数値更新は
  即時（アニメーションを挟むと操作感が鈍る）。
- 数値は既存 `fmtPreviewNum`（L3028）を再利用し、桁の見え方を他画面と揃える。
- 新規領域を作らず既存 PREDICT タブ内に収める。タブ名だけ `SIMULATE` に変更。

## 10. テスト方針

### 10.1 既存テストは無改修で通ること
`.treg` を変更しないため、以下は**内容を変えずに全通過**が条件。落ちたら設計違反。

```bash
python tests/test_light_parity.py
```

### 10.2 新規テスト

| 対象 | 内容 |
|---|---|
| 自己整合性（最重要） | `seed_rows[i].values` を rawRow として `predictRow` に渡した予測値が、同じ行だけのCSVをバッチ予測した結果と**一致**すること。スライダー経路とCSV経路の乖離をここで検出する |
| `slider_spec` 妥当性 | `min <= p1 <= median <= p99 <= max`、`hist` の合計が学習行数以下、categorical の `levels` が頻度降順 |
| 重要度集約 | 集約後の `importance_pct` 合計が 100±0.5 に収まる。one-hot / 派生 / poly / datetime_parts を含む合成データで検証 |
| `y_hist` | `counts` の合計 == `n` == `train_rows` |
| 外挿判定 | `p99` を超える値を入れたら外挿フラグが立つ／`x_clip` 境界外で予測値が変化しないこと |
| 描画スモーク | 1列のみ・全列カテゴリ・数値列50個・`rmse: null` の4ケースでレイアウトが崩れないこと |

### 10.3 手動確認チェックリスト
- 列数 1 / 5 / 20 / 50 のCSVで縦方向のレイアウトが崩れない
- R² 0.95 / 0.6 / 0.2 / 負値 の各モデルで §5.2 の減光が正しく切り替わる
- カテゴリ列のみ（数値列ゼロ）のデータで近傍ゲージが「算出不可」と出る
- ドラッグ中の FPS が体感で落ちない（LightGBM 500木 × blend 5メンバーで確認）
